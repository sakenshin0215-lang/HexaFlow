### 🚀 HexaFlow 企业级架构概览 (V1.0)

整个系统自上而下可以分为四个核心层级：

#### 1. 任务编排与状态层 (Orchestration & State Layer) —— “系统的心智与记忆”

这是 HexaFlow 能够实现“断点续传”和“混合调度”的基石。

* **混合工作流引擎 (Hybrid Workflow Engine)：** 允许你将任务定义为有向无环图 (DAG)。节点可以是“硬编码 Python 脚本”（比如精准的点击某个固定 XPath），也可以是“Agent 任务”（比如让 AI 分析当前页面的数据并决定下一步）。
* **全局状态机 (State Machine & Context Manager)：** 实时记录当前任务执行到了哪一步、各个账号的 Cookie/Token 状态、以及当前页面的 DOM 快照。
* **持久化存储：** 任务执行的每一步状态都会落盘（比如存入类似本地 SQLite 或你之前了解的本地数据库中）。一旦崩溃，系统重启后直接读取最后一次成功的状态继续执行。

#### 2. 多智能体协作枢纽 (Multi-Agent Hub) —— “系统的智能大脑群”

根据你的要求，AI 不再是一个单点，而是一个分工明确的专家团队：

* **任务规划师 (Planner Agent)：** 接收初始任务目标，结合你预设的业务模版，快速生成或组装出针对该任务的专属工作流（Workflow Blueprint）。
* **路由与调度员 (Router Agent)：** 在流程执行中，如果遇到非结构化分支，负责决定“下一步该调用哪个子模块或硬脚本”。
* **异常修复专家 (Healer Agent)：** 当“硬流程”报错（如找不到元素、页面超时）时被唤醒。它会读取报错日志、当前页面截图或 DOM 结构，尝试自我修复（比如发现页面结构变了，重新生成选择器，或者发现是被反爬拦截了，调用相应的绕过策略）。
* **领域专家助手 (Specialist Agents)：** 比如你提到的“弹窗处理助手 (Popup Agent)”，专门负责在页面突然被弹窗遮挡时，精准识别并关闭它；或者“数据解析助手”，专门负责提取复杂页面的信息。

#### 3. 隔离执行层 (Isolated Execution Layer) —— “系统的机械手臂”

为了满足“多账号并发”且互不干扰的需求：

* **多上下文管理器 (Multi-Context Manager)：** 基于浏览器自动化工具（如 Playwright），为每个账号分配完全独立的 Browser Context（独立的缓存、Cookie、代理 IP、User-Agent 等），实现物理级别的隔离。
* **行为沙盒 (Action Sandbox)：** 执行所有的点击、输入、滑动等原子操作，并将执行结果（成功、超时、拦截）向上汇报给状态层。

#### 4. 监控与人工干预层 (Human-in-the-Loop & Observability) —— “系统的安全底线”

* **挂起与警报机制：** 当 Healer Agent 尝试了 3 次依然无法修复错误时，系统将该任务实例“挂起 (Suspend)”，保存现场上下文，并通过日志或消息通知人工。
* **人工接管接口：** 允许你手动介入，比如在本地接管浏览器完成滑块验证码，或者手动点掉一个极其罕见的广告，然后点击“继续 (Resume)”，工作流就会从你介入后的状态继续往下跑。



HexaFlow 的核心运行时框架将由以下几个引擎组成：

### 🦅 HexaFlow 动态生成与执行框架

#### 1. 动态编排引擎 (Dynamic Blueprint Generator)

这是流程的起点。你输入一段自然语言 Prompt（例如：“在某个 DEX 上循环刷 10 笔交易，每次间隔随机，处理好授权弹窗”）。

* **Planner Agent** 不会直接去操作浏览器，而是生成一份 **JSON/YAML 格式的初始蓝图 (Initial Blueprint)**。
* 这份蓝图定义了：预期步骤、依赖的工具（如 `click_element`, `sign_wallet`）、状态检查点（如 `check_balance`）。

#### 2. “先锋”执行与记忆录制 (Vanguard Execution & Trace Recording)

这是你提到的“边执行边记录”的核心。第一个账号（先锋账号）带着初始蓝图进入战场：

* **状态观测器 (State Observer)：** 每次动作前，获取当前页面的 DOM 树或截图，评估“当前在哪”。
* **动态路由与修复 (Router & Healer)：** 如果页面结构符合预期，执行“硬代码”动作。如果突然弹出一个预料之外的验证码或风险提示弹窗，Healer Agent 实时介入，调用视觉或 DOM 分析工具解决问题。
* **影子记录仪 (Shadow Recorder)：** **这是最关键的一环。** 先锋账号走过的**正确路径**（包括被 Healer 修复后的新路径），会被系统实时收录，沉淀为一份**“黄金轨迹 (Golden Trace)”**，存入本地记忆库（类似于你用来做本地 AI 记忆管理的底层逻辑）。

#### 3. “克隆”重放与拟人化注入 (Clone Replay & Humanoid Injection)

当任务交给第二个、第三个账号时，它们不再需要从零开始让大模型去猜，而是直接加载刚刚生成的“黄金轨迹”。

* **降级为硬流程主导：** 此时 80% 的工作转化为确定性的硬流程，大大节省了 Token 消耗和等待时间。
* **拟人化编排器 (Stealth/Humanoid Controller)：** 这是你提到的“非常规操作任务流”。引擎会在确定性的节点之间，动态注入**非确定性行为**。比如：基于贝塞尔曲线的鼠标轨迹偏移、随机的页面上下滚动、输入框的模拟退格重打等，确保每个账号的行为指纹（Behavioral Biometrics）独一无二。

#### 4. 实时工具箱 (Real-time Tool Registry)

AI 之所以能解决未知问题，是因为它有手有脚。我们需要定义一套标准的 Tool Call 接口，让 Agent 在遇到卡点时可以随时调用：

* `DOM解析器`、`OCR识别`、`验证码接码平台API`、`Web3钱包交互脚手架` 等。




这是一个极其务实且极具工程智慧的决策！放弃在常规流程中强依赖视觉大模型，转而采用 **DOM + URL 强校验（预留视觉接口） + 录制与回放（Record & Replay） + 人工审批（Human-in-the-loop）** 的模式，能够将执行速度和成功率提升到一个全新的数量级，这在对时效性要求极高的自动化场景中至关重要。

# 🚀 HexaFlow: 企业级混合智能自动化引擎

## 1. 核心设计理念 (Core Philosophy)

HexaFlow 不是一个纯粹让 AI “自由发挥”的玩具，而是一个以**高执行率、高确定性**为底色的工业级 RPA（机器人流程自动化）系统。它的核心运作哲学是：**“一次探索，人工定调，无限克隆，智能兜底”**。

系统生命周期分为三个核心阶段：

1. **先锋录制模式 (Vanguard Record)：** 接收大模型生成的初始任务蓝图，驱动浏览器执行。每执行一步，`Trace Recorder` 都会静默记录当前的 URL、核心 DOM 结构片段（Context Snapshot）以及具体的操作（Action）。
2. **审批与固化 (Human Verification)：** 录制生成的“黄金轨迹 (Golden Trace)”以 JSON 或 YAML 格式呈现，人工可以快速 review，剔除冗余动作，确认无误后落盘固化。
3. **克隆回放与自愈 (Clone Replay & Heal)：** 多个账号并发加载固化后的轨迹。执行前进行 URL 和 DOM 的“前置断言 (Pre-check)”。如果断言通过，瞬间执行硬编码动作；如果断言失败（页面异动、弹窗拦截），唤醒 `Healer Agent` 接管，调用各种 Tool 尝试修复，修复成功后状态机回拨，继续执行。

## 3. 核心数据结构：黄金轨迹 (Golden Trace DSL)

为了让系统能够完美实现你提到的“状态检测”和“硬/软混合执行”，我们需要定义一套强大的领域特定语言（DSL）。以一个动作节点（Node）为例，它在 JSON 中大概长这样：

```json
{
  "step_id": "confirm_transaction_01",
  "description": "点击交易确认按钮",
  "pre_check": {
    "expected_url_contains": "/swap/confirm",
    "expected_dom_selector": "button#confirm-tx",
    "timeout_ms": 5000
  },
  "action": {
    "type": "click",
    "target": "button#confirm-tx",
    "humanoid_delay": [500, 1200] 
  },
  "on_error": {
    "strategy": "call_agent",
    "agent_name": "healer",
    "fallback_action": "suspend_for_human"
  }
}

```

**解析：**

* 引擎到达这一步时，会先执行 `pre_check`。如果当前 URL 不对，或者 DOM 里找不到这个按钮，直接阻断，触发 `on_error`。
* `on_error` 中定义了兜底策略：先叫 `healer` 尝试分析 DOM 修复；如果 `healer` 搞不定，就挂起任务 (`suspend_for_human`)，保存现场，等待人工介入。

## 4. 关键技术选型建议

* **底层语言与异步：** Python 3.10+，深度使用 `asyncio`。因为 IO 密集型网络请求和多账号浏览器控制，异步是唯一的性能出路。
* **浏览器驱动：** **Playwright**。原生支持多 Context 隔离，速度极快，是目前做复杂自动化（尤其是涉及大量动态交互的现代前端页面）的绝对首选。
* **数据校验与防呆：** **Pydantic**。强烈建议用它来定义所有的配置、Agent 输出结构和 Trace JSON。在大模型生成 JSON 时，Pydantic 可以做强制类型检查，防止 AI 产生幻觉输出错误格式导致系统崩溃。
* **本地状态存储：** **SQLite**。轻量、无需配置，非常适合用来做断点续传的状态机持久化。
